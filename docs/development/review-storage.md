# 审阅存储：稳定性与性能（设计稿）

此页保留上游 Edda 文件型审阅的历史设计。Margin 独立运行时已切换到
[SQLite 事务文档后端](../backend/margin.md)，不再遵循下文“不引入 SQLite”的前提。

状态：阶段 1–4 已落地（事件改存 `events.jsonl` 暂缓，见阶段 4）。

前提：坚持「一篇论文 / 一个审阅单元就是一个文件夹，附属全部是文件」，不引入 SQLite。审阅数据仍在 `reviews/<id>/` 下：`manuscript.md`、`review.json`、`revisions/*.md`。

## 一、基线（2026-10-21）

样本：真实审阅稿 RACER 的副本，`review.json` 698 KB（2 天的使用量），批注 62 条、事件 257 条。Rust 计时为 release 构建中位数；应用内计时来自隔离测试版。

`review.json` 的构成：

| 内容 | 大小 |
|---|---|
| 42 条 `edit` 事件 | 431 KB（其中 2 条作者编辑各记了 3.7 万–7.8 万字的前后文，合计 370 KB） |
| `baselineText`（与 `revisions/<基线>.md` 重复） | 125 KB |
| 批注、回复及其事件 | 约 30 KB |

每次操作的耗时（Rust 为 release 构建中位数；应用内为优化构建的隔离测试版）：

| 操作 | Rust 处理 | 应用内 IPC | 文件监听回声 |
|---|---|---|---|
| 自动保存（读盘核对 + 写文件 + 记编辑） | 9.6 ms | 记编辑 18 ms（另有读盘、写文件两次调用） | 再整份重读 13–18 ms，结果不变 |
| 新建批注 | 3.0 ms | — | 再整份重读 |
| Agent 写批注（MCP） | 3–5 ms | 前端整份重读 12–30 ms，每次约 400 KB | — |

注：最初在 debug 构建的测试版里测得 IPC 66–87 ms，其中约三分之二是未优化的 Rust（debug 下 `open_unit` 34 ms、序列化 17.5 ms），不能代表发布版，上表已改用优化构建重测。

结论：读写 JSON 本身只要 1–2 ms，Rust 一侧的时间主要在锚点重算与比对。端到端的浪费在于每次把约 400 KB 的完整状态传给前端、自身写入的回声整份重读，以及文件随编辑记录持续变大。

并发：两个写入者同时各写 40 条批注，只留下 39–40 条，另有 0–6 次读到空的 `review.json`。原因是读改写没有锁，且所有原子写共用固定的临时文件名 `{name}.tmp`。MCP 写入经全局的任务中心锁排队，Agent 之间不会冲突；冲突发生在 Agent 与应用自身的写入之间。

## 二、阶段

### 阶段 1：稳定性（已落地）

- 每个审阅单元一把写锁（`store::lock_unit`），所有读改写函数都在锁内完成。
- 原子写的临时文件名每次唯一，并带 `.edda-rename-` 标记（文件监听报为目标的内容修改）；审阅的状态、正文与快照写入前刷盘（`AtomicOpts::DURABLE`）。
- 保存前保留完整的上一版 `review.json.bak`，`review.json` 读不出时自动用备份。
- 结果：同样的并发测试 80/80 条全部保留、无读取错误；刷盘使保存多约 8 ms（后台线程）。

### 阶段 2：正文保存进锁（已落地）

审阅编辑器保存 `manuscript.md` 走通用的文件写入（插件 `writeTextFile`，原地写、不在审阅锁内），随后再调用一次记编辑。Agent 替换正文若落在两者之间，可能覆盖作者刚保存的内容。改为一个审阅命令 `review_save_manuscript`：锁内核对磁盘内容、原子写正文、记编辑，一次 IPC 完成（原来是读磁盘核对、写文件、记编辑三次）。

### 阶段 3：只传变化（已落地）

- 写命令返回变化的批注、新增事件与正文哈希，不再返回完整状态；前端只需本轮（基线以来）的事件，基线正文只在基线变化时传。
- 后端给每次写入一个版本号，文件监听报来的自身写入直接跳过，不再整份重读。
- `reviews/` 下任何变化都会触发 `review_list`，逐个读取所有单元的 `review.json`；改为只重读变化的单元。
- 实现：`ReviewView`（本轮事件、全部 Agent、按需的基线正文、`stamp`），`review_state_stamp` 过滤回声，`review_list` 按 stamp 缓存摘要。
- 结果（优化构建、同一份数据）：每次回复从约 400 KB 降到 140 KB（剩下的大头是本轮里两条整篇的作者编辑记录，见阶段 4）；自身写入的回声从整份重读 13–18 ms 变为 1–3 ms 的 stamp 比对；`review_list` 命中缓存 7–10 ms；自动保存一次调用 26–59 ms（含正文与状态两次刷盘），Agent 批注后的重读 11–37 ms。

### 阶段 4：文件结构

- 一次保存中的多处改动分段记录（`ops::edit_spans`），不再记成一整段（**已落地**）。
- 不再在 `review.json` 中存 `baselineText`（读取时本来就以快照文件为准）（**已落地**）。
- 结果（真实稿件副本）：第一次保存后 `review.json` 从 698 KB 降到 571 KB；文首、文末各改一处的保存记为两条几个字的事件，原来是一条约 7.8 万字的事件。之后每次保存只增加改动本身的大小。
- 暂缓：事件改存只追加的 `events.jsonl`。分段记录之后文件只随改动本身增长，现有的大事件来自旧记录、不会再新增；每次保存的耗时主要在锚点重算与刷盘，拆文件收益不大，却要多一个文件与格式迁移。文件再明显变大时再做。

每个阶段完成后用同一套基准和并发测试对比上面的基线。
